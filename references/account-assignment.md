# 发布账号分配：一稿多平台 ＋ 本批严格分散 ＋ 跨批均衡（account-assignment）

用户默认**不指定**每篇稿件的发布账号，账号由本文件的规则自动分配。

**三条规则，优先级不同：**

1. **多平台（硬规则，2026-10-28 用户定）**：每篇文章**一次发多个媒体**——案例稿与配对科普稿，
   **每篇都要发到搜狐号和头条号各一次**，不能只发一个平台就收工。
2. **分散（硬规则）**：同一批里**一个账号只接一个发布单元**，不允许"一个账号发多篇"。
3. **均衡（软目标）**：在此前提下，本批该用**哪几个**账号按**累计已发布篇数**从少到多挑，
   让各账号的长期累计篇数逐步缩小差距。

规则 1、2 优先。均衡不能让任何账号在本批接第 2 个单元。
"多平台"与"不重复投"不冲突：**跨平台要发全，同一平台内不重复**。

## 1. 账号池

| 项 | 规则 |
|---|---|
| 来源 | 发布账号注册表 `~/.dsh/media-publish/accounts.yaml`（GUI 设置页「新增账号」写入） |
| **派生方式** | **每次分配都从注册表重新派生**——不要手写固定账号清单。账号会不断增加，手写清单必然过时 |
| 纳入 | **默认纳入全部登录态有效的账号** |
| 排除 | 登录态失效/未登录的账号不参与分配——先登录再纳入 |
| **平台筛选** | 可按平台限定（例如只发搜狐号＋头条号：`--only-media sohu,toutiao`）。**平台筛选是唯一的人工开关**：新增**同平台**账号自动纳入，无需改代码或清单 |
| 不指定 | 除下列情形外**不需要**逐篇指定账号：用户明确指定、该篇有平台适配要求、某账号已达当日限额 |

**当前注册表（2026-10-27，12 个账号）**

| 平台 | 账号代号 | 数量 |
|---|---|---|
| 搜狐号 | `a-1`、`b-1`、`c-1`、`e-1`、`f-1` | 5 |
| 头条号 | `a-2`、`b-2`、`c-2`、`e-2`、`f-2`、`d-2`、`g-2` | 7 |
| 合计 | — | **12** |

- 本表只是**当前快照**，分配时一律以注册表为准，不要抄这份表。
- 目前注册表里**没有 CSDN 账号**；CSDN 只在确实有已登录账号时才用（旧批次用过的 `c-1`／`c-2`
  现在分别是搜狐号与头条号，**不要按旧账派活**）。
- 账号加进来后必须在 GUI 或 `media_account {op:"login"}` 完成登录，
  **没有登录态文件 = 不能派活**；12 个账号刚注册、尚未登录时，分配会因"无可用账号"停下，
  这是正确行为，不要绕过。

### 1.1 登录态判据（证据分级，别只看一个布尔值）

| 级别 | 判据 | 说明 |
|---|---|---|
| 1（最强） | **发布链路自己的会话检查**：对目标账号跑一次 dry run，能走到提交前 | 与实际发布走同一条路径，最可信 |
| 2 | 通用「检查登录态」命令 | 可用，但**有假阴性**：实测某搜狐号账号该命令报 `invalid`（"后台页面正文为空"），同账号 dry run 却 14/14 全通。**这类账号不该被排除** |
| 3（最弱） | 仅"存在登录态文件" | **不等于有效**：实测某头条号账号有登录态文件但已失效（跳扫码登录页）。仅凭此判定会把稿派给登不上的账号 |

**规则**：优先用级别 1；用级别 2 时必须记录证据来源；**不得**仅凭级别 3 就派活
（工具实现里缺省 `login_ok=false` 正是为此）。出现"命令说无效、dry run 却能走通"的分歧时，
**以 dry run 为准**并把分歧记下来。

## 2. 分配单位：发布单元（不是单篇，也不是单次提交）

```
1 个发布单元 = 1 篇案例稿 ＋ 1 篇配对科普稿
             × 每个平台各发一次（默认 搜狐号 1 个账号 ＋ 头条号 1 个账号）
             = 4 条发布
```

- **每篇都要发到每个平台**：案例稿在搜狐号、头条号各一条；科普稿同样各一条。
  只发了一个平台算**没完成**，交付说明要写明缺哪一边（SKILL §7.6）。
- **同一平台内只发一个账号**：一篇稿不会在搜狐号投两个账号，也不会在头条号投两个账号。
- **同一账号内顺序固定**：案例稿先发，科普稿随后（SKILL §7.6）。
- **一个账号本批最多接 1 个单元**。接了 1 个单元 = 该账号本批发 2 条（案例稿＋科普稿），
  只承接了**1 篇文章（1 家企业）**——这正是用户要的"不要一个账号发多篇"。
- 该账号本批的负载记为 **2 篇**；搜狐号日限 5 篇，因此一个账号一天接 1 个单元
  （4 篇里它占 2 篇）是安全的。

**单批容量 = min(各平台可用账号数)**

| 注册表现状 | 容量 |
|---|---|
| 搜狐号 5 个、头条号 7 个 | **5 个单元**（受搜狐号限制） |

超过容量的单元会开第 2 轮复用账号（见 §3.1）。
某个平台**一个可用账号都没有**时直接报错——**不要悄悄降级成单平台发布**。

## 3. 算法（按轮分配，每个平台各自挑，可判定、可复现）

```
输入：账号池 P（仅登录态有效的账号）、平台集合 M（默认=池中出现的平台）、
      本批单元 N 个、各账号累计负载 L(a)
初始化：load(a) = L(a)，batch(a) = 0，round = 0，容量 cap = min_{m∈M} |P_m|
剩余 ← 本批全部单元（按编号升序）
while 剩余 非空:
    round += 1
    若 round > 1 且 --no-wrap → 报错停下（不硬塞）        # 保护"不重复账号"
    used ← ∅
    for 单元 in 剩余（编号升序）:
        for 平台 m in M:
            cand = { a ∈ P_m | a ∉ used 且 当日已发数(a) + 2 ≤ 当日限额(a)
                             且 （未给 --max-per-account 或 batch(a) < 上限） }
            若某个平台的 cand = ∅ → 整个单元顺延到下一轮（不半个单元半平台地发）
            a* = cand 中 load 最小者；并列取**账号代号升序**
        load(·) += 2; batch(·) += 1; used ← used ∪ 本单元各平台选中的账号
    若这一轮一个都没分出去 → 报错（限额或上限已用尽），停下
输出：编号 → {平台: 账号} 的分配表（带回轮次）、各账号本批单元数、累计负载前后、是否严格分散
```

**性质**

- **第 1 轮内每个账号最多 1 个单元**，因此 N ≤ cap 时，N 个单元必然落到**每平台 N 个不同账号**
  （严格分散，本批没有任何账号接 2 个单元）。
- 只有当 **N > cap** 时才会开第 2 轮，此时个别账号接 2 个单元——
  这是用户允许的例外，**必须写进交付说明**，不能默认发生、也不能不声明。
- 同一轮内按累计负载挑账号 ⇒ 需要"下一批换几个账号"时，长期累计仍在收敛；
  并列时按代号升序 ⇒ **同一输入必得同一结果**，可复现、可审计。

### 3.1 本批篇数不能超过单批容量？不，可以，但要声明

| 情形 | 处理 |
|---|---|
| N ≤ cap | 正常。N 个单元 → 每平台 N 个不同账号，严格分散 |
| N > cap（默认） | 开第 2 轮复用账号；报告里打印 `⚠ 有账号接到多个单元`，**交付说明必须写明**哪几个账号接了 2 个单元 |
| N > cap（加 `--no-wrap`） | 直接报错并给出缺口，等用户加账号或减篇数 |
| 某平台无可用账号 | **报错**（不会降级成单平台）。加账号或用 `--only-media` 缩小平台范围 |
| 账号未登录 | 该账号不可用；若可用账号数因此不足，按上面几行处理，**不要拿未登录账号凑数** |

**写稿前就该算容量**：篇数由用户指定，但 `cap` 是硬上限。写之前先算
`min(各平台可用账号数)`，若用户要求的篇数超出，先告知"这批只能严格分散到 X 个单元，
超出部分会复用账号，是否继续"，不要写完 20 篇才发现只能分散到 5 个单元。

### 3.2 账号池扩容时的行为

新增账号（负载 0）会进入池子，并在**同平台**内被优先挑中（负载最小）。
因为每批最多 1 个单元／账号，新账号不会"一次吃很多篇"——这正是分散规则带来的副作用，
无需再加护栏。**跨平台增删要一起看**：只加头条号不会抬高 `cap`，因为 `cap` 由最少的平台决定。

平台筛选仍然有效：被排除平台的账号既不参与分配，也不参与均衡统计。

## 4. 每日限额

平台有单账号每日发文上限（实测搜狐号主号当日提示"今天还能发 5 篇"；一个单元占 2 篇）。
`daily_limit` 与 `today_published` 都拿到时，**剩余额度不足 2 篇**的账号从**本轮**候选集中剔除，
顺延到次小负载账号；顺延后仍无账号可用则报错停下。

拿不到当日计数时**不要猜**：按无限制处理，但在交付说明里写明
"未取得当日发文计数，未做当日限额约束"。

## 5. 负载从哪来

按可靠性排序，取第一个可得的：

1. **台账（首选）**：每发一条追加一行 `时间 / 编号 / 账号 / 平台 / 链接`，累计数由台账统计。
   台账是独立文件，天然可审计。**多平台后同一篇稿在两个平台各记一行**（案例稿 2 行、科普稿 2 行），
   一个单元共 4 行；台账里的"篇数"与"单元数"不是一回事：分配看**单元**，台账统计看**篇**。
   **不按平台分行记就会少算一半负载**——务必带平台字段。
2. **发布工具的运行记录**：按账号统计"真实发布且未失败"的运行次数
   （`scripts/assign_accounts.py --from-runs <运行记录目录>`）。
   ⚠ **会漏计手工驱动的发布**：实测 5 篇里有 2 篇是 agent 接真机手工点完的，**没有留下成功运行记录**，
   结果是 a-2 少算 1 篇、b-1 少算 1 篇（脚本口径得 `{a-1:2, a-2:1, b-1:0}`，真实是 `{a-1:2, a-2:2, b-1:1}`）。
   用这个来源时必须在交付说明里声明，并尽快补上台账。
3. **兜底**：拿不到任何历史计数时，按"仅本批"分配（每账号 1 个单元），
   并**必须在交付说明里写明**"历史计数不可得，本次仅做本批分散"，不得假装已全局均衡。

## 6. 输出与记录

分配必须在**发布之前**产出，并写进交付说明：

| 项 | 内容 |
|---|---|
| 分配表 | 单元编号（= 稿件编号）→ {搜狐号: 账号, 头条号: 账号} → 轮次 |
| 平台覆盖 | 本批是否两个平台都发全；缺哪个平台、为什么（不得静默降级） |
| 分散结论 | 本批 N 个单元落到每平台几个不同账号；是否**严格分散**（无人接 2 个单元） |
| 复用说明 | 若开了第 2 轮：哪几个账号接了 2 个单元、为什么（N > cap） |
| 累计负载 | 分配前 / 分配后的各账号累计与极差 |
| 账号池 | 可用账号数、单批容量 cap、被平台筛选排除的账号、未登录被排除的账号 |
| 限额说明 | 是否取得当日计数与限额 |
| 来源说明 | 负载取自台账／运行记录／仅本批 |

发布完成后，账号与链接按 SKILL §7.3 回写来源表格；**表格没有媒体列时不要新增列**，
账号归属以**台账**为准，并在交付说明里逐篇列出"编号 → 平台 → 账号 → 链接"。

## 7. 命令示例

```bash
# 账号池 + 历史负载写在一个 JSON 里（负载优先用 --ledger 覆盖）
python scripts/assign_accounts.py --accounts accounts.json --numbers 1,2,3

# 推荐：台账为负载来源 + 只发搜狐号/头条号
python scripts/assign_accounts.py --accounts accounts.json --ledger 发布台账.jsonl \
    --numbers 1,2,3 --only-media sohu,toutiao

# 5 个单元、12 个账号（搜狐 5 / 头条 7）→ 每平台 5 个不同账号，严格分散
python scripts/assign_accounts.py --accounts accounts.json --numbers 1,2,3,4,5

# 禁止复用账号（超出单批容量直接报错，不硬塞）
python scripts/assign_accounts.py --accounts accounts.json --numbers 1,2,3,4,5,6 --no-wrap

# 自测：多平台分配、容量边界、可复现性
python scripts/assign_accounts.py --self-test
```

`--json` 输出的每个单元形如：

```json
{"number": 1, "accounts": {"sohu": "a-1", "toutiao": "a-2"}, "media": "sohu,toutiao", "round": 1}
```

`accounts` 是逐平台的账号映射，**发布时按平台取值**；`account` 字段仅保留为兼容（= 首个平台）。

`accounts.json` 形状：

```json
[
  {"code": "a-1", "media": "sohu",    "login_ok": true, "daily_limit": 5, "today_published": 0, "published_count": 2},
  {"code": "a-2", "media": "toutiao", "login_ok": true, "daily_limit": null, "today_published": 0, "published_count": 2},
  {"code": "b-1", "media": "sohu",    "login_ok": true, "daily_limit": null, "today_published": 0, "published_count": 1}
]
```

`published_count` 缺省视为 0；`login_ok` 缺省视为 **false**（拿不到登录态就不派活）。

退出码：`0` 分配成功；`2` 账号池为空、全部超限、某平台无账号，或超容量且加了 `--no-wrap`。
