# 发布账号自动分配与均衡（account-assignment）

用户默认**不指定**每篇稿件的发布账号。发布账号由本文件的规则自动分配。
规则的目标不是"随机打散"，而是**让每个可用账号的累计发布篇数尽量相等**。

---

## 1. 账号池

| 项 | 规则 |
|---|---|
| 来源 | 发布账号注册表（每个账号至少有：账号代号、所属平台、登录态） |
| **派生方式** | **每次分配都从注册表重新派生**——不要手写固定账号清单。账号会不断增加，手写清单必然过时 |
| 纳入 | **默认纳入全部登录态有效的账号** |
| 排除 | 登录态失效/过期的账号不参与分配——先修复登录再纳入 |
| **平台筛选** | 账号池可按平台限定（例如只发搜狐号＋头条号，把 CSDN 排除）。**平台筛选是唯一的人工开关**：新增**同平台**账号自动纳入，无需改代码或清单 |
| **扩容** | 账号数变化**不需要改任何代码或清单**。新账号自动进入池子，并按下面的算法被喂到与其他账号追平 |
| 不指定 | 除下列情形外，**不需要**逐篇指定账号：用户明确指定、该篇有平台适配要求、某账号已达当日限额 |

**一稿一账号。** 同一篇稿件只发到一个账号，**不得**为了"覆盖更多平台"把同一篇稿复制到多个账号
（重复内容会触发平台判定，且不是用户要的"均衡"）。

### 1.1 登录态判据（证据分级，别只看一个布尔值）

| 级别 | 判据 | 说明 |
|---|---|---|
| 1（最强） | **发布链路自己的会话检查**：对目标账号跑一次 dry run，能走到提交前 | 与实际发布走同一条路径，最可信 |
| 2 | 通用「检查登录态」命令 | 可用，但**有假阴性**：实测某搜狐号账号该命令报 `invalid`（"后台页面正文为空"），同账号 dry run 却 14/14 全通。**这类账号不该被排除** |
| 3（最弱） | 仅"存在登录态文件" | **不等于有效**：实测某头条号账号有登录态文件但已失效（跳扫码登录页）。仅凭此判定会把稿派给登不上的账号 |

**规则**：优先用级别 1；用级别 2 时必须记录证据来源；**不得**仅凭级别 3 就派活
（工具实现里缺省 `login_ok=false` 正是为此）。池子里应保留每个账号的判据来源，
出现"命令说无效、dry run 却能走通"的分歧时，**以 dry run 为准**并把分歧记下来。

---

## 2. 均衡口径：按累计篇数，不是只按本批

这是最容易做错的一点。

> 若只在本批内轮询（第 1 篇给账号 1、第 2 篇给账号 2……），
> 那么**每一批都从同一个账号开跑**，长期看文章会持续堆在靠前的账号上，根本谈不上均衡。

正确口径：以每个账号的**累计已发布篇数**为负载 `L(a)`，新文章分配给**当前负载最小**的账号。

---

## 3. 算法（贪心最小负载，可判定、可复现）

```
输入：账号池 P（已排除登录态失效者）、本批篇数 N、各账号历史负载 L(a)
初始化：load(a) = L(a)（a ∈ P）
按稿件编号升序遍历本批每一篇：
    cand = { a ∈ P | 当日已发数(a) < 该账号当日限额(a) }     # 未给限额则不设限
    若 cand 为空 → 停下报告（不要硬塞给已超限的账号）
    选 a* = cand 中 load 最小者；并列时取**账号代号升序**（保证同一输入必得同一输出）
    load(a*) += 1
输出：编号 → 账号 的分配表，以及分配后各账号负载与极差
```

**性质**

- 贪心最小负载使最终极差**最小**；当 N ≥ 账号数且无人为限额时，最终极差 ≤ 1。
- 若各账号历史负载本身相差很大，一次分配**拉不平**——只能靠后续批次逐步拉近。
  此时必须把"分配前极差 / 分配后极差"一起记录，用来判断是否在收敛。
- 并列时按代号升序 ⇒ **同一输入必然得到同一分配结果**，可复现、可审计。

### 3.1 账号池扩容时的行为（新增账号会自动追平）

新增一个账号（负载 0）后，算法会**持续把新文章喂给它**，直到它的累计负载与其他账号持平；
在此之前负载高的账号会暂时不再接活。这是"自动适应账号数量"的正常表现，不是异常。

实测：3 账号负载 `{a-1:4, a-2:4, d-1:0}`，本批 4 篇 → 4 篇全部给 `d-1`，分配后 `{4,4,4}`，极差 0。

两点提醒：

- 新账号可能**一次性接走较多文章**（有多少吃多少，直到追平）。若担心新账号短时间发文过密，
  用 `--max-per-account <n>` 给"本批单账号上限"加护栏；上限用尽后按次小负载顺延，
  全部用尽则**停下报告**（不硬塞）。
- 追平只在**同平台、且未被平台筛选排除**的账号之间发生。被排除平台的账号既不参与分配，
  也不参与均衡统计——否则均衡目标会被一个根本不用的账号带偏。

---

## 4. 每日限额

平台有单账号每日发文上限（实测搜狐号主号当日提示"今天还能发 5 篇"）。
`daily_limit` 与 `today_published` 都拿到时，超限账号从候选集中剔除，顺延到次小负载账号。

拿不到当日计数时，**不要猜**：按无限制处理，但在交付说明里写明
"未取得当日发文计数，未做当日限额约束"。

---

## 5. 负载从哪来

按可靠性排序，取第一个可得的：

1. **台账（首选）**：每篇发布成功后追加一行 `时间 / 编号 / 账号 / 平台 / 链接`，
   累计数由台账统计。台账是独立文件，天然可审计。
2. **发布工具的运行记录**：按账号统计"真实发布且未失败"的运行次数
   （见 `scripts/assign_accounts.py --from-runs <运行记录目录>`）。
   ⚠ **会漏计手工驱动的发布**：实测 5 篇里有 2 篇是 agent 接真机手工点完的，**没有留下成功运行记录**，
   结果是 a-2 少算 1 篇、b-1 少算 1 篇（脚本口径得 `{a-1:2, a-2:1, b-1:0}`，真实是 `{a-1:2, a-2:2, b-1:1}`）。
   用这个来源时必须在交付说明里声明，并尽快补上台账。
3. **兜底**：拿不到任何历史计数时，按"仅本批均衡"分配，
   并**必须在交付说明里写明**"历史计数不可得，本次仅做到本批均衡"——不得假装已全局均衡。

---

## 6. 输出与记录

分配必须在**发布之前**产出，并写进交付说明：

| 项 | 内容 |
|---|---|
| 分配表 | 稿件编号 → 账号 → 平台 |
| 分配前 | 各账号累计负载、极差 |
| 分配后 | 各账号累计负载、极差 |
| 是否达标 | 极差 ≤ 1（达标）／极差是否较分配前收窄（收敛中） |
| 限额说明 | 是否取得当日计数与限额 |
| 来源说明 | 负载取自台账／运行记录／仅本批 |

发布完成后，把账号与链接按 SKILL §7.3 回写来源表格。

---

## 7. 命令示例

```bash
# 账号池 + 历史负载写在一个 JSON 里
python scripts/assign_accounts.py --accounts accounts.json --numbers 76,83,80,73,79

# 历史负载直接从发布工具的运行记录统计
python scripts/assign_accounts.py --from-runs "~/.dsh/media-publish/runs" \
    --accounts accounts.json --numbers 76,83,80,73,79

# 只算不落盘（默认就是只打印）
python scripts/assign_accounts.py --accounts accounts.json --numbers 1,2,3,4,5 --json
```

`accounts.json` 形状：

```json
[
  {"code": "a-1", "media": "sohu",    "login_ok": true, "daily_limit": 5, "today_published": 0, "published_count": 2},
  {"code": "a-2", "media": "toutiao", "login_ok": true, "daily_limit": null, "today_published": 0, "published_count": 2},
  {"code": "b-1", "media": "toutiao", "login_ok": true, "daily_limit": null, "today_published": 0, "published_count": 1}
]
```

`published_count` 缺省视为 0；`login_ok` 缺省视为 **false**（拿不到登录态就不派活）。

退出码：`0` 分配成功；`2` 账号池为空或全部超限。
