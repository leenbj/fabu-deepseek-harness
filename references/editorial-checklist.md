# 编辑核查表（事实层 / 单篇 / 跨稿）

本文件是 `fabu-deepseek-harness` 的自检依据。三张表按顺序使用：先事实层，再单篇，最后跨稿。
每一项都给出**不通过时怎么改**，不要只判"通过／不通过"。

---

## A. 事实层检查表（逐条对来源核，不能只看搜索摘要）

| # | 检查项 | 判定标准 | 不通过时怎么改 |
|---|---|---|---|
| A1 | 来源真实可打开 | 链接能打开，且是原文页而非搜索页、聚合页或 404 | 换回原文；找不到原文就删掉该陈述 |
| A2 | 来源已读原文 | 已打开原文核对（AnySearch `extract` 取全文），而非仅凭摘要或标题 | 打开原文；打不开则该来源作废 |
| A3 | 来源权威性 | 政府、行业权威机构、权威媒体优先 | 只有低权威来源时，降低表述强度或不用 |
| A4 | 发布日期已记录 | 记录文章发布日 | 补记；查不到就写"发布日期不详" |
| A5 | 事件日期／统计期已记录 | 记录事件发生日或数据所属期间 | 补记；统计期久远的要写出统计期 |
| A6 | 新旧已区分 | 明确标为原文／转载／往期旧闻 | 转载要回溯原文；旧闻不得称"最新" |
| A7 | 来源支撑对应陈述 | 每条来源标注它支撑正文哪一句 | 支撑不了的陈述删掉，或换来源 |
| A8 | 企业事实有出处 | 企业全称、业务事实来自用户提供的资料 | 资料没有的一律不写，必要时询问用户 |
| A9 | 域名有出处 | 域名来自用户资料，且后缀为".网址" | 后缀不符或缺域名时按 SKILL §2.5 上报冲突 |
| A10 | 启用事实依据正确 | 稿外写明"用户统一确认（未经独立联网核验）" | 未核验却写"已验证"必须改回 |
| A11 | 无编造来源 | 不存在拼凑、推测或生成的链接与数据 | 立即删除，并在稿外说明缺口 |
| A12 | 无越界推论 | 未把行业增长写成公司增长、政策发布写成企业参与、行业需求写成企业能力 | 改写为"行业层面如何 ＋ 企业在这条线索上的位置" |
| A13 | 无虚构功能与效果 | 未出现在线报修、下单、查询等功能，未声称提升排名、流量、成交率、信任、业务质量 | 删除；改为解释名称对应、访问识别、信息查找 |
| A14 | AnySearch 限制已披露 | AnySearch 不可用（配额/key/网络）时在稿外写明，且未用内置搜索顶替 | 补写限制说明，不留空白 |
| A15 | 无近期消息时已说明 | 改用稳定背景时在稿外注明 | 补写"本期未检索到可用的近期公开消息" |

## B. 单篇检查表（每篇都要过一遍）

**B1–B6 与 B21–B25 由 `scripts/draft_check.py` 机器核对**（`--dir "<项目文件夹>"`），
其余项人工过。机器只核字面与位置，核不了事实真伪。

| # | 检查项 | 判定标准 | 不通过时怎么改 |
|---|---|---|---|
| B1 | 标题含企业名称 | 企业全称，或**资料中已明确出现**的简称；**名称不得缺席** | 补入名称；其余部分过长就精简其余部分，不许删掉企业名 |
| B2 | 标题不只是裸域名 | 域名只能作为标题的一部分 | 重写为完整新闻标题 |
| B3 | 标题无广告腔 | 无"震撼""领先""必选""首选""重磅"等口号词 | 换成事实性表述 |
| B4 | 标题非工商登记式 | 不是"某公司成立于某年，注册资本某万元" | 改为有报道角度的标题 |
| B5 | **首两段出现完整启用事实** | 第 1 或第 2 自然段含"企业全称 ＋ 官网启用 ＋ **完整域名**"，且三者**逐字**出现 | **必改项**：把事实提进前两段；不得拖到第 3 段及以后 |
| B6 | 事实句完整、不用指代 | 三要素齐全；域名必须写出本体，不能只写"中文域名""该域名""这一域名" | 补齐要素；把域名写出来 |
| B26 | **启用事实融入行文** | 事实写在句子／段落之中，**不是独立成段的公告句** | **必改项**：把事实并进业务或环节那一段，前面加承接句 |
| B27 | 承载段的承接内容 | 含域名的那一段**非空白字符 ≥ 100 且 ≥ 2 句** | 一句独占一段必然不合格；与相邻内容合并成段 |
| B7 | 后缀唯一 | 标题与正文只出现".网址"，无其他后缀的举例或比较 | 删除其他后缀的举例与比较 |
| B8 | 篇幅达标 | 正文中文字符 900–1150（含中文标点，不含空白） | 偏离时按 SKILL §6.1 处理并在稿外说明 |
| B9 | 无灌水 | 没有为凑字数重复同一意思的段落或句子 | 删除重复段，宁可短 |
| B10 | 不照抄经营范围 | 不是经营范围原文的搬运 | 用业务事实重新组织语言 |
| B11 | 不堆砌工商信息 | 成立日期、注册资本、法人、地址未成堆出现 | 只保留与报道角度有关的一条，其余删除 |
| B12 | 无制作过程用语 | 无"企业资料介绍""据表格""写作测试""企业资料显示" | 直接删除，不用替换词 |
| B13 | 无虚构采访 | 无引号内的杜撰引语、无"记者走访""现场看到" | 删除，改为客观陈述 |
| B14 | 无冒充署名 | 没有媒体名或记者署名 | 删除署名 |
| B15 | 无购买号召 | 无"快来注册""立即抢注""不容错过" | 删除 |
| B16 | 无宏大空话 | 无"赋能新时代""开启新篇章"式空转 | 换成具体事实 |
| B17 | 价值解释不越界 | 只解释名称对应、访问识别、信息查找 | 删除效果类承诺 |
| B18 | 视角客观克制 | 无过度形容与情绪化表达 | 收敛用词 |
| B19 | 角度非模板 | 不是"企业介绍→业务→域名优势→产业升级"四块 | 重排结构与段落顺序 |
| B20 | 稿外附属齐全 | 来源清单、启用依据、缺料说明、实测字数、核心问题一句话 | 补齐后再交付 |
| B21 | **标题长度** | 总长（含标点、不含空格）**≤ 30 字** | 精简标题其余部分；**不要省略企业名** |
| B22 | **择名规则** | 设标题长 `T`、标题中名称长 `N`、全称长 `F`：`T−N+F ≤ 30` → 必须用**全称**；`> 30` → 用**简称** | 该用全称却用了简称就换成全称；该用简称却硬塞全称就先精简标题 |
| B23 | 简称来源正当 | 标题中的简称必须是**资料里已明确出现**的写法 | 不用自造写法，也不截取半个品牌名 |
| B24 | **首两段用全称** | 标题用了简称时，正文第 1 或第 2 自然段**仍必须出现企业全称** | 正文不得一路用简称，也不得用"该公司"顶替首段主体 |
| B25 | 启发式判定已复核 | 机检的实体识别不确定时，已用 `--full/--short/--domain` 显式指定后重跑 | 未复核的机检结论不算通过 |

> B5／B6 是这一节最容易被忽略的两项：把域名写成"中文域名"、或用"该公司"代替企业全称，
> 都算不合格——因为读者要看到的是**可核对的完整事实**。

## C. 跨稿检查表（两篇及以上时必做）

| # | 检查项 | 判定标准 | 不通过时怎么改 |
|---|---|---|---|
| C1 | 标题并排可区分 | 各篇标题句式明显不同 | 改写句式，不要只换公司名 |
| C2 | 前两段并排可区分 | 导语落点与推进方式不同 | 重写导语 |
| C3 | 核心问题可概括且互不相同 | 每篇能用一句话说清"要回答什么"，且这些话不一样 | 重新选定角度，再重写 |
| C4 | 开篇类型有变化 | 不都是行业开篇，也不都是企业事件开篇 | 至少一篇换开篇类型 |
| C5 | 段落推进链不同 | 不是同一套段落顺序换词 | 重排推进链 |
| C6 | 论证路径不同 | 不是"都先讲行业、再讲企业、最后讲域名" | 调整论证顺序与落点 |
| C7 | 结尾方式不同 | 不都是"迈向高质量发展"式收尾 | 换收尾方式（回到事实、回到服务对象、回到环节变化等） |
| C8 | 事实重点不同 | 各篇突出的业务事实不是同一条 | 换重点事实支撑角度 |
| C9 | 非批量替换 | 差异不是把同义词换掉得来的 | 属于替换式的，重写而非替换 |
| C10 | 无重复句且无重复推进 | 既无重复句，也无雷同的推进链与论证路径 | 雷同的整段重写 |

> 提醒：**没有重复句 ≠ 内容真正不同。** C5、C6、C9 比 C10 前半句更重要。

## E. 判定口径速查

- **"约 1000 中文字"**：默认 900–1150；低于 900 必须说明原因；不得拉长灌水。
- **"事实密度"**：资料可支撑的独立事实条数。1–2 条事实却写 1200 字，一定是灌水。
- **"可核验"**：能被读者用给出的链接与日期独立复核。
- **"无法核验"**：必须在稿外写明，不得在正文里用模糊表述掩盖。
- **自检结论**：写清"通过了哪些项、哪些项因资料或联网条件无法核验"，不写"质量已保证"。

## F. 相似度量化检查表（硬门槛，整批必做）

口径全文见 [`similarity-metric.md`](similarity-metric.md)；参考实现 `scripts/similarity_check.py`。

```bash
python scripts/similarity_check.py --dir "<项目文件夹>"
```

| # | 检查项 | 判定标准 | 不通过时怎么改 |
|---|---|---|---|
| F1 | 正文相似度（5-gram Jaccard） | 同批**任意两篇** ≤ **10%** | 按 F6 顺序改角度与结构，**不许换同义词** |
| F2 | 标题相似度（2-gram Jaccard） | 同批**任意两篇** ≤ **15%** | 换标题句式（背景句＋事实 / 冒号＋议题 / 从…到…） |
| F3 | 最长逐字重合片段 | 报告数值；**> 20 字**必须人工复看 | 该片段所在段落重写，不是改几个词 |
| F4 | 规范化口径 | 已剔除企业名、域名与必写套语；字母小写、去标点 | 口径不一致则数值不可比，先统一口径再比 |
| F5 | 实测数值已记录 | 稿外写出**实测值与所用口径** | 只写"已检查相似度"视为未检查 |
| F6 | 超标整改顺序 | 换开篇类型 → 换报道问题 → 换推进链 → 换论证路径 → 换结尾落点 → 最后才换句式 | 顺序颠倒会白改；改完重跑 |
| F7 | 反复不达标 | 回到 SKILL §5.1 重新选题 | 说明两篇报道问题实质相同，磨字句无用 |
| F8 | 定性检查同时通过 | C1–C10 与 F1–F2 **两者都过**才达标 | 字面达标不等于内容不同，见 similarity-metric 第六节 |

**F 节单独通过 ≠ 达标。** 相似度指标只约束字面重合，无法发现"论证路径照搬、每句重写"的稿子；
因此 C 节（定性）与 F 节（定量）必须同时通过，缺一不可。

## G. 表格回写检查表（仅用户授权后执行；契约见 `table-writeback.md`）

| # | 检查项 | 判定标准 | 不通过时怎么办 |
|---|---|---|---|
| G1 | 授权 | 用户**明确**授权回写本表 | 未授权则只写独立文件，一个字都不回写 |
| G2 | 列义核对 | 动格前已**逐列打印样例**（前 3 行 + 非空率/长度），据实值判定列义 | 表头写错或残留数据值是常态，凭列字母猜必错 |
| G3 | 备份 | 写前已生成 `<表名>-备份-<时间戳>.xlsx`，路径写进交付说明 | 没备份不写 |
| G4 | 定位唯一 | 按域名列定位，命中**恰好一行** | 0 行或多行 → 停下报告，不模糊匹配、不任选 |
| G5 | 白名单 | 只改：编号列 / 状态列 / 媒体列账号 / 末尾链接列 | 越界即返工；链接列**只新增一列** |
| G6 | 状态机 | `已写作` 只在稿件**已交付**时写；`已发布` 只在**拿到公开链接**时写 | 审核中/只有预览 id → 停在 `已写作`，链接留空 |
| G7 | 只前进 | 已 `已发布` 不被降级为 `已写作` | 降级请求 → 报告并跳过 |
| G8 | 幂等 | 重复执行同状态产生 0 处差异 | 有差异说明写错了列或行 |
| G9 | 口径差异上报 | 状态列原值为旧口径（如 `已完成`）时，只改本次涉及的行，其余保持原样并**如实报告** | 擅自批量改写整列 = 越权 |
| G10 | 逐格验证 | 用备份与新表**逐格对比**，改动集合与预期集合完全一致 | 多出任何一格都要查清并回滚 |

**G10 是唯一能证明"没越界"的手段**，别用"我看了一遍"代替。

## H. 发布账号分配检查表（不逐篇指定账号时必做；契约见 `account-assignment.md`）

| # | 检查项 | 判定标准 | 不通过时怎么办 |
|---|---|---|---|
| H1 | 账号池 | 只纳入**登录态有效**的账号；**从注册表派生，不手写固定清单** | 手写清单必然漏掉新增账号；失效账号先修登录，绝不派活 |
| H1b | 登录态判据 | 以"跑一次 dry run 能走到提交前"为准 | 通用检查命令对搜狐号有**假阴性**（报 invalid 而 dry run 全通）；"存在登录态文件"≠有效 |
| H1c | 平台筛选 | 被排除平台的账号不参与分配，**也不参与均衡统计** | 让不用的账号参与统计会把均衡目标带偏 |
| H1d | 扩容 | 新增账号自动进池并追平；必要时用 `--max-per-account` 护栏 | 新账号会"有多少吃多少"直到追平，属正常；不要因此写死清单 |
| H2 | 不指定 | 没有逐篇硬编码账号（用户明确指定的除外） | 逐篇硬编码会让均衡失效 |
| H3 | 负载口径 | 用**累计**已发布篇数，**不是**本批内轮询 | 只用本批 ⇒ 每批都从同一账号开跑，长期仍堆在少数账号 |
| H4 | 负载来源 | 台账优先；若用工具运行记录，必须声明"会漏计手工发布" | 漏计会把文章偏向被少算的账号（实测少算 a-2 一篇、b-1 一篇） |
| H5 | 可复现 | 同一输入两次分配结果一致（并列按账号代号升序） | 引入随机会破坏可审计性 |
| H6 | 均衡结果 | 报告分配前/后极差；篇数足够时极差 ≤ 1 | 极差未收窄要说明是"篇数不足"还是"历史负载差距过大"，不是算法问题 |
| H7 | 每日限额 | 超限账号从候选集剔除，顺延次小负载 | 全部超限则**停下报告**，不硬塞给已超限账号 |
| H8 | 一稿一账号 | 同一篇不派给多个账号 | 复制到多账号＝重复内容，不是均衡 |
| H9 | 记录 | 分配表（编号→账号→平台）与前后极差写进交付说明 | 没记录就无法审计"到底均不均衡" |

**若拿不到任何历史计数**，允许只做本批均衡，但必须在交付说明里写明限制——
不得把"本批均衡"说成"账号间已均衡"。
